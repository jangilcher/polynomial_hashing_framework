# JSON Format for Configuration Files

This document describes the JSON format for configuration files used by `run.py`.

A configuration file contains a list of hash implementations/configurations to build, test, benchmark, and plot.
Each configuration is specified as a JSON object.
As a consequence of that the order of fields does not matter.
Furthermore the parsing ignores any custom additional fields,
but we do not recommend creating custom fields in your config,
as new fields might be added when new features are added to the framework.

Each configuration entry is either:
- a **reference configuration**, which benchmarks an external/reference implementation; or
- a **generated hash configuration**, which benchmarks a polynomial hash implementation generated by the framework.

For the old legacy format, see `docs/old_grammar.md`.

## Top-level file structure

A JSON configuration file can use either a wrapper structure or a plain list of configurations.

The recommended form is the wrapper structure:

```json
{
  "name": "Configuration file example",
  "description": "Optional description of configuration file",
  "configurations": [
    {
      "name": "Example of reference configuration",
      "ref": true,
      "lib": "sodium",
      "mac": "poly1305",
      "implementation": null
    },
    {
      "name": "Example of generated hash configuration",
      "ref": false,
      "keysize": 16,
      "blocksize": 16,
      "tagsize": 16,
      "field": {
        "field_type": "binary",
        "size": 128
      },
      "wordsize": 64,
      "limbs": [64, 64],
      "multiplication": {
        "method": "schoolbook",
        "options": null
      },
      "key_transform": {
        "id": 1,
        "options": null
      },
      "msg_transform": {
        "id": 1,
        "options": null
      },
      "field_transform": {
        "id": 1
      },
      "hash_transform": {
        "name": "simple_key_reuse_length_encoding"
      },
      "polynomial": {
        "name": "MyPoly",
        "num_keys": 1,
        "parameters": [],
        "inner_polynomial": null,
        "test": { "name": "MyPoly" }
      },
      "keygenerator": {
        "required": false,
        "number_of_bytes": null
      },
      "description": "optional description of configuration"
    }
  ]
}
```

For small files, a plain list is also accepted:

```json
[
  {
    "name": "Example configuration",
    "ref": true,
    "lib": "sodium",
    "mac": "poly1305",
    "implementation": null
  }
]
```

## Common configuration fields

Every configuration entry has the following common fields:

| Field | Type | Required | Description |
|---|---:|---:|---|
| `name` | string | yes | Name used in logs and plots. |
| `ref` | boolean | yes | `true` for a reference configuration, `false` for a generated hash configuration. |
| `skip` | boolean | no | Optional. If `true`, the configuration is ignored by `run.py`. Defaults to `false`. |
| `description` | string | no | Optional description. |


## Reference configurations

A reference configuration selects a supported external implementation through a `(lib, mac, implementation)` triple and has the following format (optional fields are indicated with a `?` after their type):

```js
{
  "name": str,
  "ref": true,
  "lib": str,
  "mac": str,
  "implementation": str | null,
  "skip": bool?,
  "description": str?
}
```

### Example

```json
{
  "name": "OpenSSL GMAC",
  "ref": true,
  "lib": "openssl",
  "mac": "gmac",
  "implementation": null
}
```


### Supported reference implementations

The following reference implementaions are currently supported:

| `lib` | `mac` | `implementation` |
|---|---|---|
| `sodium` | `poly1305` | `null` |
| `openssl` | `poly1305`, `gmac` | `null` |
| `haclstar` | `poly1305` | `null`, `"128"` (SSE, 128bit vectors), `"256"`  (AVX, 256bit vectors) |
| `haberdashery` | `gmac` | `"broadwell"`, `"haswell"`, `"skylake"`, `"skylakex"`, `"tigerlake"` |
| `hash2l` | `hash_128` | `"karatmult3"`, `"sbmult3"` |
| `hash2l` | `hash_256` | `"karatmult1"` |
| `d2lHash` | `d2lHash1271`, `d2lHash1305` | `"d2_g4"`, `"d2_g8"`, `"d3_g4"`, `"d3_g8"`, `"d4_g4"`, `"d4_g8"`, `"d5_g4"`, `"d5_g8"` |
| `polyhash` | `poly1305` | `"g1"`, `"g4"`, `"g8"`, `"g16"`, `"g32"` |


## Generated hash configurations

A generated hash configuration selects a polynomial implementation, field arithmetic, byte/field transforms, and key-generation behavior to build a framework-generated polynomial hash function.
It has the following format (optional fields are indicated with a `?` after their type):

```js
{
  "name": str,
  "ref": false,

  "tagsize": int,

  "keysize": int,
  "keygenerator": KeyGeneratorSpec,

  "field": FieldSpec,
  "wordsize": 32 | 64,
  "limbs": [int],

  "multiplication": MultiplicationSpec,

  "polynomial": OuterPolynomialSpec,

  "blocksize": int,
  "key_transform": KeyTransformSpec,
  "msg_transform": MsgTransformSpec,
  "field_transform": FieldTransformSpec,
  "hash_transform": HashTransformSpec?,

  "skip": bool?,
  "description": str?
}
```

### Required fields

In addition to `name` and `ref`, supply all fields in this table:

| Field | Type | Meaning |
|---|---|---|
| `tagsize` | integer | Output tag size in bytes. |
| `keysize` | integer | Number of key bytes encoded per field element or key block. |
| `keygenerator` | `KeyGeneratorSpec` object | Whether the framework uses key generation that is benchmarked. Defined below. |
| `field` | `FieldSpec` object | Prime or binary field selection. Defined below. |
| `wordsize` | `32` or `64` | Word size in bits used by the generated arithmetic. |
| `limbs` | array of integers | Bit width of each field-element limb used by the generated arithmetic. |
| `multiplication` | `MultiplicationSpec` object | Type of field arithmetic generated. Defined below. |
| `polynomial` | `OuterPolynomialSpec` object | Select polynomial, parameters, optional inner polynomial, and test hook. Defined below. |
| `blocksize` | integer | Number of message bytes encoded per field element or message block. |
| `key_transform` | `KeyTransformSpec` object | Key-to-field encoding selection. |
| `msg_transform` | `MsgTransformSpec` object | Message-to-field encoding selection. |
| `field_transform` | `FieldTransformSpec` object | Field-to-output encoding selection. |


`hash_transform` is optional. It controls explicit hash-level length encoding, as described below. The common `skip` and `description` fields are also optional.


### Example

```json
{
  "name": "Classical Polynomial 128",
  "ref": false,
  "tagsize": 16,
  "keysize": 16,
  "keygenerator": {
    "required": false,
    "number_of_bytes": null
  },
  "field": {
    "field_type": "binary",
    "size": 128
  },
  "wordsize": 64,
  "limbs": [64, 64],
  "multiplication": {
    "method": "schoolbook",
    "options": null
  },
  "polynomial": {
    "name": "classical_2level_NB_UPK_Delay_a",
    "num_keys": 1,
    "parameters": [8],
    "inner_polynomial": null,
    "test": {
      "name": "classical_polynomial"
    }
  },
  "blocksize": 16,
  "key_transform": {
    "id": 1
  },
  "msg_transform": {
    "id": 1
  },
  "field_transform": {
    "id": 1
  },
  "hash_transform": {
    "name": "simple_key_reuse_length_encoding"
  }
}
```

### Key generation/specification

Polynomials can require key material of either fixed length or of variable length that depends on the message length.

When it requires a small fixed amount of key material, `keysize` represents this amount in bytes and the generation of this key material is not benchmarked. 
When the amount of key material is large and/or depends on the message length, the key material is generated through a key generator and this key generation is benchmarked.

The `keygenerator` field controls whether the framework calls the key generator.
A `KeyGeneratorSpec` is one of the following:

**— No Key Generator:**

```json
"keygenerator": {
  "required": false,
  "number_of_bytes": null
}
```
**— Using Key Generator for key expansion:**

```json
"keygenerator": {
  "required": true,
  "number_of_bytes": null
}
```

If `required` is `true`, the selected polynomial implementation should provide a function:

```c
unsigned long long get_keylength(unsigned long long inlen);
```
in the polynomial C header, that computes the keysize required to process a message of length `inlen`, including any length-encoding adjustment implemented by the construction.


### Fields and arithmetic

The framework automatically generate the arithmetics for certain types of finite fields. 
We note that a syntactically valid specification is not a validation of the field or generated arithmetic.

#### Field specification

The `field` object selects the field used by the generated arithmetic.
A `FieldSpec` is one of the following:

**— Crandall prime, `p = 2^pi - delta`:**

```json
{
  "field_type": "crandallprime",
  "pi": int,
  "delta": int
}
```

**— Mersenne prime, `p = 2^pi - 1`:**

```json
{
  "field_type": "mersenneprime",
  "pi": int
}
```

**— binary field of size `2^size`:**

```json
{
  "field_type": "binary",
  "size": int
}
```

For binary fields, `run.py` chooses the reduction polynomial from [`src/field_arithmetic/bf_polynomial_coeffs.py`](../src/field_arithmetic/bf_polynomial_coeffs.py). 



#### Word size and limb layout

The arithmetic layout is controlled by `wordsize` and `limbs` which must be chosen together with the field. 
For example, `[44, 44, 42]` is a three-limb, 130-bit layout for the Poly1305 field, whereas `[64, 64]` is the two-limb layout used by the binary-field example above.
Each limb must be smaller or equal to the `wordsize`.

#### Multiplication specification

The `multiplication` object selects which type of field arithmetic is generated by the framework for the selected field.
A `MultiplicationSpec` has the following format:

```js
{
  "method": "schoolbook" | "karatsuba",
  "options": [MultiplicationOptions] | null
}
```

`schoolbook`is currently the only type of arithmetic supported/generated.
`karatsuba` implementations is left for future work.


The supported options are:

| Option | Effect in the runner |
|---|---|
| `precompute` | Enables precomputed multiplication/squaring support for compatible fields. |
| `cmulreduction` | For binary fields only. Enables the use of `clmul` carryless multiplication instead of shifts during field reductions. |
| `doublecarry` | Enables the corresponding flag in the prime-field generators. |
| `doublecarryover` | Enables the corresponding carry-over flag in the prime-field generators. |
| `doublecarrytemp` | Enables the `doublecarry_temp` flag in the prime-field generators. |



**Example**

```json
{
  "method": "schoolbook",
  "options": ["precompute", "doublecarry"]
}
```


### Polynomial specifications

The `polynomial` field selects the polynomial construction which can be a one or two-level construction.
An `OuterPolynomialSpec` has the following format:

```js
{
  "name": str,
  "num_keys": int?,
  "parameters": [int],
  "test": {
    "name": str
  } | null,
  "inner_polynomial": InnerPolynomialSpec | null,
  "options": ["inline_inner"] | null
}
```

| Field | Description |
|---|---|
| `name` | C polynomial implementation name under `src/polynomial/`. |
| `num_keys` | Optional. Value passed to the C macro `NUM_KEYS`; its interpretation depends on the construction. In general, it is the number of field-element keys consumed by the outer polynomial. Defaults to `1`. |
| `parameters` | Integer parameters passed to the C macros `OUTER_PARAM0`, `OUTER_PARAM1`, etc. Use `[]` when no parameters are needed. Parameter meanings and valid combinations are specific to each C implementation, not specified by the JSON model. |
| `test` | Optional. Sage/Python test name used by the correctness tests. |
| `inner_polynomial` | Optional. Select a lower-level polynomial for two-level constructions along with its parameters, and a test hook. Defined below. |
| `options` | Optional. Select outer-polynomial code-generation options. Currently supports `"inline_inner"` which defines the C macro `ALWAYS_INLINE_INNER`. |

#### Correctness-test selection

`polynomial.test.name` selects a Python method named `test_<name>` in [`tests/test_polynomial.py`](../tests/test_polynomial.py). 
That method constructs the appropriate model from [`tests/polynomial.sage`](../tests/polynomial.sage). 

The C name and test name can differ.
For a two-level hash, provide test names for both levels. 
The runner skips hash-level tests if the outer test specification is absent, or if a configured inner polynomial lacks its test specification. 


#### Inner polynomial

The current implementation supports one level of nesting. That is, an outer polynomial may have an inner polynomial, but the inner polynomial should not itself have another inner polynomial.

An `InnerPolynomialSpec` has the following format:
```js
{
  "polynomial": PolynomialSpec,
  "superblocksize": int,
  "superkeysize": int
}
```

| Field | Description |
|---|---|
| `polynomial` | Select lower-level polynomial specification. Defined below. |
| `superblocksize` | Number of message blocks processed by one lower-level instance. Value passed to the C macro `NB_SUPERBLOCKS`. |
| `superkeysize` | Number of key blocks used by one lower-level instance. Value passed to the C macro `NB_SUPERKEYS`. |


The inner `PolynomialSpec` object has the same structure as an outer polynomial object `OuterPolynomialSpec`, except that it does not use the outer-only `inner_polynomial`, `num_keys` and `options` fields:

```js
{
  "name": str,
  "parameters": [int],
  "test": {
    "name": str
  } | null
}
```

For an inner polynomial, `parameters` become the C macros `INNER_PARAM0`, `INNER_PARAM1`, and so on. 


#### Example of two-level polynomial

```json
"polynomial": {
  "name": "tMMH",
  "num_keys": 1,
  "parameters": [],
  "inner_polynomial": {
    "polynomial": {
      "name": "NMH_NB_Delay",
      "parameters": [8, 1, 0, 1],
      "test": {
        "name": "NMH"
      }
    },
    "superblocksize": 24,
    "superkeysize": 24
  },
  "test": {
    "name": "tMMH"
  },
  "options": ["inline_inner"]
}
```

### Transform specifications

Transforms describe how byte strings are mapped into field elements and how field elements are mapped back into output bytes. 
They are identified by their transform IDs.

The supported transform IDs are defined by the framework encoding tables in `src/framework_encodings.py`.
The key, message, and output tables are separate: an ID valid in one table is not necessarily valid in another.

Some fields below use the `HexInt` type, which is either an integer or a string representing an integer in hex.

#### Key transform

A `KeyTransformSpec` has the following format:
```js
{
  "id": int,
  "options": {
    "mask": HexInt
  } | null
}
```

Example for key clamping:

```json
"key_transform": {
  "id": 11,
  "options": {
    "mask": "0x0ffffffc0ffffffc0ffffffc0fffffff"
  }
}
```

#### Message transform

A `MsgTransformSpec` has the following format:
```js
{
  "id": int,
  "options": {
    "byte": HexInt,
    "mask": [HexInt],
    "encodeLSB": bool
  } | null
}
```

Example of implicit encoding:

```json
"msg_transform": {
  "id": 3,
  "options": {
    "byte": "0x01",
    "mask": ["0xffffffffffffffff"],
    "encodeLSB": false
  }
}
```

#### Field-to-output transform

A `FieldTransformSpec` has the following format:
```js
{
  "id": int
}
```

Example:

```json
"field_transform": {
  "id": 1
}
```



### Length encoding

The optional `hash_transform` field selects explicit length encoding that can be applied to a compatible polynomial implementation. 

It has the following format:

```js
{
  "name": LengthEncodingName | null
}
```

Currently supported names are:

```text
additive_length_encoding
multiplicative_length_encoding
key_reuse_length_encoding
simple_key_reuse_length_encoding
```

Example:

```json
"hash_transform": {
  "name": "simple_key_reuse_length_encoding"
}
```
